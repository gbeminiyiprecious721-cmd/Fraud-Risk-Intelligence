## Things worth knowing before picking this up again

- **Environment:** `.venv` now has pandas/numpy/pytest/matplotlib/**scikit-learn 1.9.1/scipy 1.18.1** (Stage 5). `.venv-1` is still empty and unused — resolve that duplication before it matters, not urgently. `requirements.txt` now exists at the project root (added in Stage 5's final-verification round, `pip freeze` against `.venv`) — no `pyproject.toml` yet.
- **pandas 3.1.0 infers plain strings as `StringDtype`, not `object`.** Any dtype-based logic must check for `"str"`/`"string"` too. Hit once already (Stage 2's `classify_columns`), fixed, now routinely reused (`src/preprocessing.py` depends on that fix).
- **Three-way split, not two:** `docs/_stage4_split_assignment.csv` has `train`/`validation`/`final_test` (70/15/15 by time, no gap — reasoned, not default). **Always access partitions via `src.leakage_boundaries.get_partition()`**, never a raw filter of that file — `final_test` is refused by default and only returns rows with `allow_final_test=True`, which should only ever appear once, in Stage 10.
- **`docs/feature_availability_register.csv` is the single source of truth for column scope** — 435 rows, every one with status/rationale/evidence-level. `src/preprocessing.py::load_included_columns()` reads it programmatically; don't hand-copy a column list anywhere else or it'll drift.
- **`include_with_caveat` (369 columns) means "eligible for controlled experiments," never "confirmed safe."** This has been stated explicitly twice now (Stage 4's review round, Stage 5's report) because it's the single easiest thing to accidentally forget once a model starts producing good numbers — a good Stage 7+ result on one of these columns does not resolve its availability question.
- **Identity data (41 columns) is still fully excluded.** Searched twice now for documentation on collection timing/mechanism, found nothing either time. Revisable with real evidence, not with a good model result.
- **`R_emaildomain`/`V`-column leakage question: half-resolved, stated precisely.** The missingness-by-fraud-status pattern is explained by `ProductCD` (ruling out one mechanism); whether the field is captured *before* the prediction-time boundary is still unverified. Don't round this up to "resolved" — an earlier draft of this did exactly that and had to be corrected.
- **D-column checks are supporting evidence, not proof.** Non-negativity + low correlation with `TransactionDT` rule out two narrow failure modes; a symmetric lookback window would pass both and still be non-causal. Same "don't round up" caution applies.
- **Stage 3's EDA ran on the full 590,540-row dataset, before the split existed.** Documented as a research-stage bias (Stage 5). The resolution going forward: Stage 3 can inform *strategy* (e.g. "this column family needs a missingness indicator"), never a *fitted parameter* — those are always recomputed on `train` only. `docs/EDA_REPORT.md`'s own numbers were never relabeled; they're still honestly full-dataset figures.
- **Sparse vs. dense isn't automatic — check the actual density.** sklearn's `ColumnTransformer` default (`sparse_threshold=0.3`) would have returned dense at this pipeline's 41.56% density; measured sparse at 1.78GB vs. dense at 2.85GB and changed the default. Don't assume "lots of one-hot/indicator columns = sparse automatically" without checking.
- **Peak process memory (~16.0-16.6GB) is much higher than the 1.78GB final output — root cause now localized, not just estimated.** `resource.getrusage()` instrumentation (Stage 5 final-verification round) pinned the jump to inside the single call `transformer.fit(train_df)` — sklearn's own `ColumnTransformer`/`SimpleImputer`/`OneHotEncoder` internals (dense intermediates + dense-to-sparse conversion before the final hstack), not this project's pandas loading code. A real, separate pandas-layer inefficiency (three functions each reading the full unfiltered file before filtering to partition rows) was found and fixed via `load_partition_df()` — but fixing it did NOT move the ~16GB figure, confirming it was never the dominant cause. float32 numeric dtype benchmarked as a validated, available mitigation (-17.2% peak, correctness preserved) but NOT adopted as the default (explicit instruction: don't switch solely because a benchmark is faster). Fine on this 64GB machine, would not be on a smaller one — still a real Stage 7+ productionization concern.
- **271 missingness indicators are 95% redundant** (Stage 5 final-verification round): 258 of 271 are exact-duplicate masks of just 13 distinct missingness patterns (26 unique patterns total) — matches what Stage 3 only gestured at qualitatively for the `V`-column block. Not deduplicated yet; a real candidate for explicit approval before Stage 6, not applied unilaterally.
- **`HistGradientBoostingClassifier` does not accept sparse input** (checked via `sklearn.utils.get_tags()`, no `.fit()` call) — conflicts with this pipeline's sparse-by-default output. Worth weighing if Stage 7 considers it.
- **The feature-availability register is now 434 rows** (was 435) — the duplicate `TransactionID` row (`train_transaction` + `train_identity`, same join key in both files) was merged post-Stage-5-approval, no feature decision changed. `docs/LEAKAGE_BOUNDARIES_REPORT.md` and `scripts/run_stage4_analysis.py` still say 435 — that's correct as an honest historical snapshot of Stage 4's own approval, not a live bug; don't "fix" them to match. `src/leakage_boundaries.py::build_feature_availability_register()` was deliberately left unchanged and would re-produce the duplicate if ever rerun from scratch.
- **A pre-written conclusion has now needed correction twice** (Stage 3's `has_identity` interpretation, Stage 4's `R_emaildomain`/D-column overclaims). The pattern: don't trust a plan for how something "probably" resolves until the actual check runs, and re-read your own draft skeptically even after it runs.
- **`data/raw/` is gitignored.** `feature_availability_register.csv` and `docs/PREPROCESSING_REPORT.md` are real deliverables, kept tracked; `_stage4_split_assignment.csv`, `_stage4_analysis_raw.json`, `_stage5_preprocessing_raw.json`, `_dataset_schema_snapshot.json`, `_stage2_validation_raw.json` are generated intermediates and gitignored.
