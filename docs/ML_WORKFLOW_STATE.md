- 2026-10-24 — Proposed PR-AUC (research metric), precision/recall@fixed-capacity (operational metric), and cost-sensitive threshold selection (decision layer) as the evaluation approach, ruling out plain accuracy — why: standard reasoning for severe class-imbalance problems (ROC-AUC can look deceptively high under imbalance; accuracy is structurally uninformative), independent of this dataset's actual (not yet measured) class balance. Alternatives considered: ROC-AUC alone (rejected, imbalance-sensitive), a fixed 0.5 threshold (rejected, not cost-optimal by construction). Validated by: methodological reasoning only — **no model exists yet, so no metric value has been computed**.
- 2026-10-24 — Did **not** invent a target performance number (e.g. "AP > 0.8") for Stage 1 success criteria — why: no baseline exists yet to anchor a number against; per `ml-engineering-workflow`'s Honest Reporting standard, a placeholder number presented as a target would be indistinguishable from a fabricated result later. - `train_transaction.csv`: 590,540 rows × 394 columns, 652 MB. Contains `isFraud` (label), `TransactionDT`, `TransactionAmt`, `ProductCD`, `card1–6`, `addr1–2`, `dist1–2`, `P_emaildomain`, `R_emaildomain`, `C1–14`, `D1–15`, `M1–9`, `V1–339` (anonymized Vesta-engineered features).
- `train_identity.csv`: 144,233 rows × 41 columns, joinable to `train_transaction` on `TransactionID`.
- `test_transaction.csv`: 506,691 rows × 393 columns — same schema as train **minus `isFraud`**.
- `test_identity.csv`: 141,908 rows × 41 columns — same schema as `train_identity`.
- `sample_submission.csv`: 506,691 rows × 2 columns (`TransactionID`, `isFraud`) — a submission template, not ground truth.

**Stage 2 (verified by actually reading the data — full detail in `docs/DATA_VALIDATION_REPORT.md`):**
- Row counts confirmed (test_identity: 141,907 data rows, the 141,908 above included the header line).
- Zero duplicate `TransactionID`s in any of the 4 ID-bearing files.
- Join coverage: train 24.42%, test 28.01%, **zero orphan identity rows either side** — confirmed structural, not a defect.
- **Chronological holdout confirmed at the train/test boundary:** `train`'s `TransactionDT` spans 86,400–15,811,131; `test`'s spans 18,403,224–34,214,345 — test starts exactly ~30 days after train ends. Refined (Round 2): this confirms the boundary, not intra-train feature availability or absence of all leakage risk — see Known Limitations.
- **Round 2 finding:** `train_identity` uses `id_01`…`id_38`; `test_identity` uses `id-01`…`id-38` — same 38 fields, different separator. Must be normalized before Stage 5 shared code.
- **Round 2:** `pytest` 9.1.1 installed, `tests/test_data_validation.py` run — 9 passed, 0 failed, 0 skipped.
- Column classification (corrected mid-stage for a pandas 3.1.0 string-dtype default): `train_transaction` = 380 numeric / 14 categorical; `train_identity` = 24 numeric / 17 categorical.
- Missingness: severe (86–97%) in specific identity sub-fields and several `D`/`V`-family transaction columns — pattern not yet explained (Stage 3).
- No value-level distributions, class balance, or feature-target relationships were inspected — that is Stage 3 (EDA) work and remains explicitly deferred.
